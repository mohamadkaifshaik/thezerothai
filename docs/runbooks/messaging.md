# Runbook: direct messages (ADR-0027)

Owner module: `backend/internal/messaging`. Plan: `docs/plans/ui-w7-messaging.md` (W7-5 SendMessage, W7-6 lifecycle and this runbook;
W7-7 and W7-8 the lists and mark-read, W7-9 accept and delete; W7-10 push; W7-11 badge; W7-12 report). Flag: `FEATURE_MESSAGING` (wire name `messaging`, default
`off`; dev ceiling allowlist 3, no prod raise before W7-22 and W7-23 pass in dev).

What exists on `main` after W7-5, W7-6, W7-7, W7-8, W7-9, W7-10 and W7-11: all six RPCs (SendMessage, ListConversations, ListMessages, MarkConversationRead, AcceptMessageRequest, DeleteConversation), the `messaging` account-deletion step, the `messages` export section, the push-only `message` type of notifications (W7-10) and the GetMe unread-conversation badge (W7-11). Sections that
describe later pieces say so. With W7-12 (this change) `ReportContent` also takes a MESSAGE target and `opsctl messages takedown` exists (section 5b).

Data (all index-free, no composite index; fieldOverrides `indexes: []` for `messages.text`, `messages.requestHash`, `dmInbox.peer`,
`dmInbox.last`, `dmRequests.peer`, `dmRequests.last`, deployed with `firebase deploy --only firestore:indexes` **before `messaging` leaves `off` in a project**, or message text is indexed):
`conversations/{convId}` (id = first 32 hex of SHA-256 of the two uids; guessable, authorization never relies on it), its `messages/{msgId}`
subcollection (id = first 32 hex of SHA-256 of sender, "SendMessage", idempotency key: the message IS the idempotency record), and the per-user
entries `users/{uid}/dmInbox/{convId}` and `users/{uid}/dmRequests/{convId}`. `quotas/{uid}.dmNew` counts new conversations per IST day. `conversations.clearedAt` and `clearedKey` are maps keyed by uid (delete for me: the time, and the digest of the DeleteConversation key, 2026-10-29 note); the eraser drops the deleted uid's keys. Client
rules stay deny-all. Messages are **not end-to-end encrypted**: the server holds the text (ADR-0027 D2).

## 1. Kill switch
`FEATURE_MESSAGING=off` (Terraform `var.feature_messaging`), then deploy; no data migration.
- **Off globally:** every RPC answers `FAILED_PRECONDITION FEATURE_DISABLED feature=messaging` with 0 reads past the account-status
  interceptor's one. The clients hide the destination, the routes and the profile Message button (they read `GetMe.enabled_features`).
  `GetMe.unread_conversation_count` is 0 reads (W7-11).
- **Rollout, not a stop:** `allowlist` with a user outside it, or `percent` 0, is a rollout. SendMessage and AcceptMessageRequest need the flag
  on **for the caller and for the recipient** (a recipient outside the cohort answers `CANNOT_MESSAGE`, byte-identical to a block). The four
  list, read, mark-read and delete RPCs only need it **not globally off**, so a user dropped from the allowlist can still read and clean up.
  Because both people need the flag, a `percent` step means "works between enabled users only"; the likely ramp is allowlist straight to `on`.
- **What stays on after `off`:** stored conversations, entries and messages (they come back with the flag), and, never flag-gated, the
  account-deletion step and the export section: cleanup and right-to-delete must run after the flag is off.
- **Push:** the fan-out sends a `message` push only when `messaging` **and** `notifications` are on for the recipient (W7-10). The send itself
  never waits for it.
- **`DEGRADED_MODE=readonly`:** the interceptor refuses the four mutations (SendMessage, MarkConversationRead, AcceptMessageRequest, DeleteConversation: `UNAVAILABLE DEGRADED_MODE`, retry after 60 s) before any read; ListConversations and ListMessages stay up.

## 2. A stuck eraser step (`messaging`)
The step runs after `follow_requests` and before `identity` (`docs/runbooks/account-deletion.md` section 6 is the job's operations guide; its
stuck-job procedure applies). Its name is persisted in `deletionJob.step`: never rename it.

Each call is one bounded unit of work (at most 500 documents) and the checkpoint is ids and counters only (`after`, `conv`, `phase`, `msg`,
`both`, `entry`, `conversations`, `tombstoned`, `entriesDeleted`). For each conversation of the user, in `__name__` order:
1. `phase ""`: pick the next conversation (`participants array-contains uid ORDER BY __name__ LIMIT 1`) and, in **one transaction**, add the uid to
   `gone` (so a send can no longer rewrite the deleted user's entries: the send transaction reads that document) and rewrite the peer's entry to the
   "Deleted account" placeholder (`peerId` = `deleted`), with the snippet "Message deleted" when the user's message was the last (peer already gone: no entry read).
2. `phase tombstone`: 500 per call, the user's messages (`senderId == uid`): `senderId` = `deleted`, and for a VISIBLE one text and `requestHash` emptied, `state = DELETED_ACCOUNT`. The peer's messages are never touched.
3. `phase finish`: delete the user's own `dmInbox` or `dmRequests` entry.
4. `phase rewrite`, when the peer lives: one transaction replaces the uid by `deleted` in `participants`, `gone`, `requestFrom`, `requestTo` and drops `clearedAt.<uid>` and `clearedKey.<uid>`.
   **It is last on purpose**: the cursor query finds the conversation through `participants`, so every earlier step keeps it findable and is idempotent, and after the rewrite there is nothing left to do.
   `gone` is never empty in between, so sends stay refused; the peer's own eraser finds the conversation by the peer's uid and sees `deleted` in `gone`.
   `phase tree`, instead, only when the peer is gone too: the messages 500 per call, then the conversation document last.

Cost for the reference account (20 conversations, 300 own messages, peers alive): about 380 reads (21 cursor queries, 20 conversation and 20
peer-entry reads, 20 conversation reads in the rewrites, 300 messages), 360 writes (20 gone marks, 20 peer entries, 300 tombstones, 20 rewrites), 20 deletes. A repeat after completion is one empty query. A step repeated after a crash re-does at most one unit and never leaves a half-erased
conversation (the crash matrix `TestAccountLifecycle_MessagingCrashAtEverySideEffect` kills the job after each of its side effects).

| Symptom | Likely cause | What to do |
|---|---|---|
| The job sits at `step=messaging`, `account_job` retries | A failed batch, or `NotFound` on a tombstone batch because the peer's eraser deleted the tree at the same moment | Both are retried by the lifecycle (`maxStepErrors`) and the redelivery sees the finished state. Look at the `messaging: ...` error in the job's log line (uids and conversation ids are redacted to hashes). If it persists, check Firestore status, then the checkpoint in `users/{uid}.deletionJob.checkpoint` |
| `messaging: mark conversation gone: ... DeadlineExceeded` (or `Aborted`) in the job's log line, once or twice, and the job then goes on | The two people of one conversation were deleted at the same moment: both `MarkGone` transactions read the conversation document and then write it, so they collide, and the loser can outlast the repo's 5 s `txTimeout`. Nothing was written (the transaction rolled back) | Nothing, if the job goes on: the lifecycle repeats the failed call with the same checkpoint (up to 5 errors in a row, then Pub/Sub redelivers, up to 10 times), and the repeat finds the finished state, so no conversation, message or entry is left behind. Act only when it persists: follow the first row and `account-deletion.md` section 6. The `TestEraser_BothDeletedConcurrently` integration test reproduces this on the emulator and applies the same retry (`eraseLikeTheJob`) |
| A conversation is still listed for a deleted user's peer, with their messages as "Message deleted" | By design (F3): the peer keeps the conversation read-only (`gone` is non-empty); it is deleted when the peer's account is deleted too | Nothing |
| `conversations/*` or `messages` documents remain after **both** accounts are deleted | The second eraser crashed after its `gone` mark and was never resumed (the lifecycle backstop re-runs the step) | Re-run the account's deletion; or delete the tree by hand: the messages (500 per batch), then `conversations/{convId}` last |
| The deleted user's uid is found in a surviving peer's conversation | Should not happen: the step ends each conversation by replacing the uid with the fixed placeholder `deleted` (`messaging.DeletedUID`) in `participants`, `gone`, `requestFrom` / `requestTo`, drops the `clearedAt` and `clearedKey` entries (maps keyed by the uid), and sets the tombstones' `senderId` and the peer entry's `peerId` to it (ADR-0027 D11). The T11 residue sweep runs on this case with no allowlist entry. A hit is a code defect or a step that never finished: re-run the account's deletion | Treat `deleted` as "Deleted account" in any reader; it resolves to no profile |

The `messaging_purge_done` line carries `conversations`, `messages_tombstoned`, `entries_deleted` and `uid_hash` (never a peer uid) when the step finishes.

**Export** (`messages` section, appended after the existing sections): `{"conversations":[...]}` newest conversation first, each with the peer's
handle **at export time** (empty and `peerDeleted: true` when the peer is gone), the state, the time stamps, and its messages newest first. Own messages carry their
full text; received ones are a time and `"received"` only (the peer's words are the peer's data, F5). No peer uid, conversation id or message id appears. Cost: one read per conversation and per message of
both sides (the section orders them), about 620 for the reference account, plus at most one directory read per 50 peers.

## 3. Abuse levers
Every limit is config (rule 11); each is per instance unless it says exact, so the ceiling is x `max-instances` (3).

| Lever | Default | Effect when hit | Where |
|---|---|---|---|
| `RATE_LIMIT_MESSAGES_SEND_PER_MIN` | 20 | `RATE_LIMITED` (60/min at 3 instances) | in memory, ratelimit interceptor |
| `MESSAGES_SENDS_PER_DAY` | 300 | `RATE_LIMITED limit=messages_daily`, retry after IST midnight (900/day at 3) | in memory, interceptor |
| `MESSAGES_NEW_ACCOUNT_SENDS_PER_DAY` | 50 | same limit name, for accounts younger than `QUOTA_NEW_ACCOUNT_WINDOW` | in memory, the send service |
| `MESSAGES_MARK_READ_PER_DAY` | 500 | `RATE_LIMITED limit=messages_mark_read_daily` on `MarkConversationRead` (W7-29, review W7-22 M-1: every call on an existing entry is 1 write, repeats included, so the 60/min default bucket alone allowed about 259k writes a day for one account; now at most 500 x 3 instances = 1,500) | in memory, interceptor |
| `MESSAGES_MUTATIONS_PER_DAY` | 500 | `RATE_LIMITED limit=messages_mutation_daily`, ONE counter shared by `AcceptMessageRequest` and `DeleteConversation` (W7-29; sized like `GRAPH_MUTATIONS_PER_DAY`); at most 500 x 3 instances x 5 = 7,500 operations per account per day | in memory, interceptor |
| `QUOTA_DM_NEW_CONVERSATIONS_PER_DAY` / `QUOTA_NEW_ACCOUNT_DM_NEW_CONVERSATIONS_PER_DAY` | 20 / 5 | `LIMIT_REACHED limit=dm_new_daily` | exact, `quotas/{uid}.dmNew`, in the send transaction |
| `MESSAGES_REQUEST_MAX_UNANSWERED` | 3 | `LIMIT_REACHED limit=request_unanswered` on the requester's 4th message until the recipient replies or accepts | exact, `conversations.requestCount`, in the send transaction |
| `RATE_LIMIT_MESSAGES_READ_PER_MIN` | 30 | the list and poll bucket (W7-7, W7-8) | in memory |
| `MESSAGES_PUSHES_PER_RECIPIENT_PER_HOUR` | 20 | pushes are skipped, messages still stored (W7-10) | in memory |
| Per-uid read budget | 2,000 reads/uid/day per instance | `RATE_LIMITED limit=read_budget_daily` | in memory |

Worst case for one sender: about 900 messages a day, of which at most 20 new conversations x 3 request messages reach strangers.
- **Block, mute and report are the user's levers.** A block either way is `CANNOT_MESSAGE` with the same bytes as a deleted account and a recipient with messaging off (no oracle). A muted sender is delivered **silently**
  (no push, no unread increment; the conversation still appears for the recipient). Requests from blocked, blocking or muted accounts are hidden from the Requests list (W7-7). Report a message: `ReportContent` with target type MESSAGE (W7-12).
- **Moderator takedown of a message** is `opsctl messages takedown CONV:MSG [--report R] [--dry-run]` (W7-12; section 5b and `docs/runbooks/moderation.md`, "Reading a message report"): it tombstones the message (`state = REMOVED`, text emptied), bumps the conversation `rev` and rewrites the inbox previews that showed it (4 writes at most); the report evidence keeps that one message.
  For an abusive account rather than one message the lever is `opsctl suspend-user` (`docs/runbooks/moderation.md`): a SUSPENDED sender is refused by the account-status interceptor and a SUSPENDED recipient answers `CANNOT_MESSAGE`.
- **Turn one lever down without a deploy:** none; limits are env vars on the `api` service, a Terraform change plus a release. Fast stop for a spam wave: `FEATURE_MESSAGING=off`, or remove the offender from the allowlist.
- **Log queries** (request line, rpc `/dzeroth.messaging.v1.MessagingService/SendMessage`): `jsonPayload.limit_name` (`messages_daily`, `messages_mark_read_daily`, `messages_mutation_daily`, `request_unanswered`, `dm_new_daily`), `jsonPayload.refused_reason`
  (`blocked`, `recipient_inactive`, `recipient_flag_off`, `gone`: the wire answer is always `CANNOT_MESSAGE`), `jsonPayload.state` (`accepted`, `request`, `new`), `jsonPayload.silent`, `jsonPayload.replay`.
  Never present: message text, snippets, peer uids, conversation ids in clear (`conversation_hash` and `uid_hash` only).
  AcceptMessageRequest and DeleteConversation (W7-9) log `kind=accept|delete`, `conversation_hash`, `state` (`accepted` / `request`), `replay` (a repeat that wrote nothing), `folder` (delete: `inbox` / `requests`),
  `refused_reason` (`recipient_flag_off` = the peer is outside the flag cohort, `gone` = the peer deleted the account; the wire answer is `CANNOT_MESSAGE` either way) and the request line's `fs_reads` / `fs_writes` / `fs_deletes`.

## 4. The polling cost trigger and how to read it
Delivery is pull (ADR-0027 D7): a visible thread polls ListMessages with `since_token` (web 15 s hot, Android 30 s hot, 45 s quiet, stopped after 5 min idle or hidden), the Inbox refreshes by
`since` on open, resume and after a push. Polling is the largest W7 cost line at 3,000 DAU (about INR 262 of INR 480 a month for CPU), so the realtime step on the stage ladder watches it.

The trigger (stage ladder row "Delivery to an open thread", **sustained 7 days**): message polls **above 25 % of all Cloud Run requests**, **or** poll vCPU-seconds above **INR 300 a month**,
**or** p95 send-to-render on an open web thread above 20 s with user complaints. Each poll per DAU per day is about INR 28 a month at 3,000 DAU (21 CPU, 3.5 requests, 3.6 reads), about 0.4 at 300.

Measure it (read-only). A poll is a ListMessages request line with `kind=poll` (W7-8; before W7-8 there are no polls and the share is 0). Cloud Logging (the same shape as `docs/runbooks/bookmarks.md`):
```
gcloud logging read 'resource.type="cloud_run_revision" AND resource.labels.service_name="api" AND jsonPayload.message="request"' \
  --project=dzeroth-prod --freshness=1d --limit=200000 --format=json \
| jq '[.[].jsonPayload] | {requests: length, polls: (map(select(.rpc == "/dzeroth.messaging.v1.MessagingService/ListMessages" and .kind == "poll")) | length)} | . + {share_pct: (100 * .polls / (.requests // 1))}'
```
For the CPU line, take the ListMessages p50 `latency_ms` of `kind=poll` lines times the poll count (billed vCPU-seconds, 0.1 s minimum per request at the worst), multiply by the vCPU-second price in `docs/reviews/cost-model.md`
section 7, and compare with INR 300. Cross-check against the Cloud Run `request_count` and `container/cpu/allocation_time` metrics for the revision. The per-uid read budget bounds one client: a web hot thread is about 288 reads an hour, so about
7 hot hours or 22 quiet hours a day, and a forgotten open thread costs at most about 11 polls. Seven consecutive days over a threshold is an ADR (owner-only Firestore listeners behind a rules ADR, then SSE); do not tune the
intervals first without the founder.

Send cost is the other measured line: SendMessage reads 5 worst cold (2.5 planning) and writes 3 (accepted), 4 (request), 5 (new conversation); the request line's `fs_reads` / `fs_writes` must stay inside those.
A new revision that exceeds them is a code defect (the budget assertions in `internal/apiserver/messaging_chain_integration_test.go` fail first).
ListMessages cost (W7-27): a **first page** reads 25 worst cold at page 20 and 55 at page 50 (interceptor, conversation, query, peer, caller graph, and the caller's own entry, which fills `unread_count` and `silent`); an **older page** 24 / 54 (no entry read); a `since` poll 3 (+1 per extra message). The first page is the only one whose request line (`kind=list_messages`, `entry_found`) shows the extra read. A missing entry (delete for me) still bills 1 read and answers 0. The same entry read serves the blocked-peer header (W7-30): when the peer blocked the caller, the thread header shows the peer snapshot frozen on the caller's entry and never the live profile (an older page and a first page whose entry is gone read "Deleted account"). The budget assertions are `TestMessagingChain_ReadBudgetTable` and `TestListMessages_FirstPageUnreadOnEmulator`.
AcceptMessageRequest costs 3 reads worst cold (interceptor, conversation, request entry; 2 when the conversation is already accepted), 2 writes (conversation state, the new `dmInbox` entry) and 1 delete (the `dmRequests` entry);
DeleteConversation 3 reads, 1 write (`clearedAt` and the key digest `clearedKey`, one update) and 1 delete (the caller's entry); a retry with the same key 2 reads (the entry is not read) and nothing written, any other repeat 3 reads and nothing written. A refused or unknown-id call stops after 2 reads. The assertions are in
`internal/apiserver/messaging_accept_delete_chain_integration_test.go`.

## 5. Test push in dev
Prerequisites: `FEATURE_MESSAGING` and `FEATURE_NOTIFICATIONS` both `allowlist` with the **same** three dev uids (both people need both flags), the `messaging` Firestore field overrides deployed to
`dzeroth-dev`, the notifications fan-out subscription healthy (`docs/runbooks/notifications.md`), and one Android handset or emulator signed in as the recipient with a registered device (RegisterDevice; web and iOS get no push, ADR-0017 D11).
1. Make the two accounts follow each other (a stranger's first message is a **request**, which never pushes), or have the recipient reply once so the request is accepted.
2. Send from account A to B (the app, or `SendMessage` with A's token). Expect the response, B's `dmInbox` entry with `unreadCount` 1, and **one** `notification_delivery` line with `type=message` (`pushed=1`) in Cloud Logging for the fan-out
   (`jsonPayload.event="notification_delivery"`). The handset shows the generic "New message" with the conversation id as its only data: no sender, no text.
3. Negative checks: a request (non-mutual) pushes nothing; a recipient who muted the sender gets the message with no push and no unread; `FEATURE_NOTIFICATIONS=off` for the recipient drops it; 21 messages inside an hour show `push_throttled` once
   `MESSAGES_PUSHES_PER_RECIPIENT_PER_HOUR` (20) is reached while every message is still stored.
4. **Mixed rollout:** an older revision that receives a `message` event drops it as `unknown_type` and acknowledges it, so a rollout can lose at most a push, never a message (ADR-0027 D9). The event carries `conversationId` additively (`v` stays 1). The push is **push-only**: no `users/{uid}/notifications` row, no badge move, never in ListNotifications. A send that stored its message but pushed nothing: check the recipient's two flags, the `suppressed` and `push_throttled` counters on the `notification_delivery` line, and the request line (`kind=send`, `state`, `silent`).
5. On the emulators (`make dev`), `NOTIFICATIONS_DELIVERY=inline` delivers in-process; the push goes to `LogSender`, so look for the `notification_push_local` log line instead of a handset.
6. **Client routing (W7-19):** tapping the push (background or cold start) opens `/messages/<conversationId>` over Home. In the foreground nothing is drawn: a push for the open conversation pulls it at once, a push for another conversation adds one to the Messages badge unless the cached Inbox row already shows it unread, it is already counted, or it is a request (a conversation counts once), and an open inbox refreshes (at most once a minute; not while a thread is open over it, then once on return). The Notifications badge and list never move for a message push, and a hot thread polls every 30 s on Android only while a push can reach it (device registered, `notifications` on, the conversation not muted and not a request); otherwise every 15 s. The client cannot see the server's 20 an hour push limiter, so a thread whose pushes are being dropped by it still polls at 30 s.

## 5b. Report a message and the moderator takedown (W7-12, ADR-0027 D12)
`ReportContent` with `target_type = MESSAGE` and `target_id = "<conversation id>:<message id>"` (32 lower-case hex each). The moderation module asks
`moderation.MessageLookup` (implemented by the messaging service; moderation never reads `conversations` or `messages`). The caller must be a
participant and the message must be the **peer's** and `VISIBLE`; the report then holds that one message's text, the sender's handle and its time
(`docs/runbooks/moderation.md` has the operator side). The existing reports quota (20 a day, 5 for a new account), the 5/min bucket and `already_reported`
on a repeat apply unchanged.
- **Flags.** `FEATURE_REPORTS` on for the caller **and** `FEATURE_MESSAGING` not globally off (F6): a user dropped from the `messaging` allowlist, or
  outside its percent bucket, can still report. `FEATURE_MESSAGING=off` answers `FEATURE_DISABLED feature=messaging` with no read past the interceptor's.
- **Cost.** 6 reads cold (interceptor, conversation, message, sender profile, report, quotas), 3 warm (message, report, quotas), 2 writes; a repeat
  at most 5 reads (2 warm), 0 writes; a refusal at most 3 (non-participant 2, cold or warm, W7-28: the cache never answers or learns from a caller who is not in the conversation; unknown message 3 cold). The conversation is the 60 s instance cache and the profile the directory's; the message is never cached. The lookup reads no flag
  state and **no graph**: a conversation with a blocked peer stays open (D4), so it stays reportable. The budget is asserted in
  `internal/apiserver/messaging_report_chain_integration_test.go`.
- **One NOT_FOUND.** An unknown conversation, a conversation the caller is not in, an unknown message, a message that is `REMOVED` or tombstoned by its
  sender's account deletion all answer the same bytes (`NOT_FOUND message not found`); the caller's own message is `VALIDATION target_id`. The log line
  has `report_target=MESSAGE`, `outcome`, `conversation_hash` and never the text or an id in clear.
- **Takedown.** `opsctl messages takedown CONV:MSG [--report R] [--note N] [--dry-run]` (the usual typed project id for `*-prod`). One transaction:
  the message becomes `REMOVED` with `text` and `requestHash` emptied (field-level updates, never a `Set`), and each participant's entry whose
  `last.messageId` is that message gets `last.snippet = "Message removed"`, `last.state = REMOVED` and `changedAt` (server time). The message also gets
  `removedAt` (server time: the record of a takedown made without `--report`), and the conversation `rev` +1 with `updatedAt` strictly later, even when
  no preview shows the message. At most 4 reads and 4 writes (message, conversation, two previews); `--dry-run` reads the same, in a read-only
  transaction, and writes nothing; a repeat, or a message the eraser already tombstoned, writes nothing. It keeps `senderId`, so the sender's later
  account deletion finds the message and leaves it `REMOVED` (the eraser only clears a `VISIBLE` message). The eraser's tombstone page writes with
  each document's `LastUpdateTime`, so a takedown that commits while a page is running is never overwritten with `DELETED_ACCOUNT`: that page
  fails once (`FailedPrecondition`), the job retries and re-reads the message as `REMOVED`. A sender's retry of the original send after a
  takedown replays the `REMOVED` tombstone (no error, no second message).
  A taken-down message never reaches the report path again (it is no longer `VISIBLE`).
- **How a takedown reaches a device that cached the thread or the inbox (ADR-0027 note 2026-10-29).** A takedown moves neither `createdAt` nor
  `lastMessageAt` (the inbox keeps its order), so two other things carry it. *Thread:* `conversations.rev` is incremented, and every ListMessages
  `since_token` carries the rev its issuer saw. The next poll with an older rev is `VALIDATION since_token` after at most 2 reads (interceptor,
  conversation; request field `since_retired=true`), the very same bytes as an expired token; the client drops the cached thread and makes one cold
  open, which shows the message removed. The conversation is read through the 60 s instance cache, so another instance can accept an old token for
  up to 60 s; a token of the new rev makes that instance drop its copy. *Inbox:* the entry's `changedAt` is set, and the ListConversations `since`
  query orders by it, so the next refresh returns the entry with the new preview (same position, `updated_at` unchanged). The eraser's
  `RewriteConversation` bumps `rev` too (the surviving peer's cached thread picks up the tombstones and the "Deleted account" header), `MarkGone` sets
  the peer entry's `changedAt`, and Accept sets it on the moved entry. A takedown is not undoable. The report keeps the evidence copy until
  resolved + 90 days. Known and deferred: a mark-read or a delete-for-me on one device does not reach the user's other devices until the next message
  or a cold open.
- **A sender whose account is not ACTIVE** (suspended, deleting) still has their `VISIBLE` messages shown in the thread, so they stay reportable;
  the evidence handle is empty and the report's owner uid names them.

## 6. Other failure modes
| Symptom | Likely cause | What to do |
|---|---|---|
| Users see `CANNOT_MESSAGE` for someone they should reach | A block either way, the recipient outside the flag cohort, the recipient not ACTIVE, or a `gone` conversation. The wire answer is the same on purpose; the log's `refused_reason` says which | Check the two accounts' graph docs and the flag cohort; a block applies at once on the instance that handled it and within 60 s elsewhere (graph snapshot cache, ADR-0027 A8) |
| `LIMIT_REACHED request_unanswered` for a user whose first messages were delivered | The requester sent 3 messages and the recipient has not replied or accepted (AcceptMessageRequest, W7-9) | Expected. The recipient's reply or Accept lifts it. **A recipient who deletes the request does not lift it**: the conversation stays a REQUEST for the sender, whose count still applies (DeleteConversation, W7-9). A retry of the 3rd message (a lost response) replays, it is never refused |
| `messaging_txn_contention` WARN (`txn_attempts` above 3) or `UNAVAILABLE busy, please retry` | Lock contention on one conversation document while it is a REQUEST (each request message updates it), or two people opening a conversation at the same moment | Expected to be rare; the client retries with the same idempotency key (a replay). A sustained rate means one pair is exchanging many request messages: the cap of 3 bounds it |
| `messaging_accept_contention` or `messaging_delete_contention` WARN with `UNAVAILABLE busy, please retry` (retry after 1 s) | An Accept or Delete lost every retry of its transaction to a concurrent write of the same conversation document: the peer's request message, the recipient's reply (which accepts), or the other person's Accept / Delete | Expected to be rare. The client may retry at once with the same key. **Accept** is idempotent by state (`ACCEPTED` never returns to `REQUEST`, so a late retry writes nothing); **Delete** is replay-safe by key (its `idempotency_key` digest is stored as `clearedKey.<uid>` with `clearedAt`, so a retry with the same key writes nothing even after the peer's next message, ADR-0027 note 2026-10-29); a Delete under a *new* key is a new delete. The conversation is never left with an entry in both folders (`TestAcceptVsDelete_Race`, `TestAcceptVsSend_Race`) |
| `ListMessages` INTERNAL in Error Reporting with a `DeadlineExceeded` cause (no `messaging_list_messages_contention` line exists) | Firestore is slow or degraded on a read. A read has no lock to lose, so it is not contention and is deliberately not mapped to `UNAVAILABLE busy`: the client retries `UNAVAILABLE` on read-only RPCs, which would multiply the polls against a degraded Firestore.
