# Firestore data model (Native mode, `(default)` database)

Only the Go API touches Firestore (Admin SDK). `firebase/firestore.rules` is **deny-all** for clients:
```
rules_version = '2';
service cloud.firestore { match /databases/{db}/documents { match /{d=**} { allow read, write: if false; } } }
```

## Indexes (`firebase/firestore.indexes.json`)
- posts: `authorId ASC, isReply ASC, createdAt DESC` (home `in` chunks + profile Posts tab, `isReply == false`)
- posts: `authorId ASC, createdAt DESC` (profile Replies tab; purge/export pages, descending)
- posts: `conversationId ASC, createdAt ASC` (threads)
- posts: `hashtags ARRAY_CONTAINS, createdAt DESC` (hashtag pages)
- posts: `authorId ASC, hasMedia ASC, createdAt DESC` (profile Media tab) and `authorId ASC, kind ASC, createdAt DESC` (profile Reposts tab), COLLECTION scope (ADR-0024 D14); queries order `createdAt DESC, __name__ DESC`. `hasMedia` and `kind` stay indexed
- follows: `followeeId ASC, createdAt DESC`; `followerId ASC, createdAt DESC` (the latter also serves ListSuggestedUsers' `followerId in [≤ 30] ORDER BY createdAt DESC` friends-of-friends query, ADR-0024 D8; no new index)
- users: `status ASC, deletionJob.progressAt ASC`; exports: `status ASC, createdAt ASC` (account-lifecycle backstop: ordered cursor scans of stuck jobs, ADR-0011 amendment 2026-10-08)
- notifications: single-field `actorIds` `array-contains` at COLLECTION_GROUP scope only (fieldOverride; the Eraser's "rows that name the deleted user" query, ADR-0017 D10)
- followRequests: `followeeId ASC, createdAt DESC` (since ADR-0003; ListFollowRequests, the `privacy_public` job's pages and the eraser's incoming pass, ADR-0025). The eraser's outgoing pass `followerId ==` uses the automatic single-field index; no new composite index (ADR-0025 D15)
- privacy: `uids` exempt from single-field indexing (fieldOverride `indexes: []`, ADR-0025 D15): at the 20,000 cap the array would otherwise hit the 40,000 index entries per document limit and cost an index write per entry; no query uses it. Acknowledged in `firebase/field-overrides.ack`
- postRemovals: `authorId ASC, createdAt DESC` (per-feed removal-log window query and the erase-by-author query; `state` stays index-exempt)
- scheduled: `status ASC, publishAt ASC` at **COLLECTION_GROUP** scope (the sweep: `status == PENDING && publishAt <= now ORDER BY publishAt LIMIT 50`; accept only refs shaped `users/{uid}/scheduled/{32 hex}`) and the same fields at **COLLECTION** scope (the list: `status in [PENDING, FAILED] ORDER BY publishAt, __name__ ASC`, cursor `(publishAt, id)`; and the ±4 min window `count()`); a collection-group index is not relied on for a collection query. The pending `count()` (`status == PENDING`, `Limit(26)`) uses the automatic single-field index. `scheduled.draft`, `scheduled.requestHash` and `posts.replyPolicy` are exempt (fieldOverrides). TTL `scheduled.expireAt` lives in Terraform `ttl_fields` (`scheduled_expire_at`), never in the indexes file (ADR-0021)
- userLikes: `recent`, `recentReposts` and `bookmarks` (ADR-0023 D3) are arrays exempt from single-field indexing (fieldOverrides, `indexes: []`); the override is deployed with `firebase deploy --only firestore:indexes` and acknowledged in `firebase/field-overrides.ack` (founder-gated files)
- users: `bannerUrl`, `bannerThumbUrl`, `location`, `website` and `pinnedPostId` exempt from single-field indexing (fieldOverrides `indexes: []`, ADR-0024 D14; no query uses them), next to `bio`, `displayName`, `avatarUrl`, `avatarThumbUrl`; acknowledged in `firebase/field-overrides.ack`
- messaging (ADR-0027, proposed; deployed by W7-3): **no composite index, no collection-group query**. fieldOverrides `indexes: []` at COLLECTION scope for `messages.text`, `messages.requestHash`, `dmInbox.peer`, `dmInbox.last`, `dmRequests.peer`, `dmRequests.last`, acknowledged in `firebase/field-overrides.ack` (both founder-gated)
- users: single-field on `handleLower` (default) for prefix search
- Exempt large text fields from indexing (`posts.text`, `users.bio`) — saves storage and write cost.

## Query rules
- Every query has `.Limit(n)`, n ≤ 50. Cursor = last doc's `(createdAt, id)` encoded opaquely.
- Tie-breaker: order `createdAt DESC, __name__ DESC` explicitly. A composite index carries `__name__` in the direction of its **last** field, so an ascending `__name__` (or an ascending `createdAt` on a DESC index) needs a new index. Timeline tokens: bindings, window tokens, 30-day TTL and the `since` settle watermark per ADR-0010 D13/D14.
- `in` filters take ≤ 30 values → chunk and merge (k-way by createdAt).
- Prefix search: `where handleLower >= q and handleLower < q + ""` limit 10.
- Transactions only where invariants need them (handle uniqueness, like/unlike toggles). Keep them small.
- Read-your-writes: after a mutation, update the instance cache from the written data instead of re-reading.
- IDs: Snowflake (time-ordered) as decimal strings for posts/media. Fine below ~500 writes/s to a collection; revisit at Stage 2.
- **A uid never contains `_`** (ADR-0008 A3). `_` is the composite-key separator in `follows`, `likes` and `reposts` doc ids, so `a_b_c` would otherwise be ambiguous. A uid matches `^[A-Za-z0-9-]{1,128}$` (`pkg/platform/ids.ValidUID`), enforced on target ids, on the caller uid in authn, and in the single `edgeID` helper in `internal/graph`. A provider or import that issues `_` needs a new ADR before it is enabled.
- Idempotency: deterministic doc ID from `hash(uid, idempotency_key)` for creates; replay returns the existing doc.

## Deletes & privacy
- Deleting a post deletes its doc and its likes/reposts in a background Pub/Sub job; timeline caches invalidated; clients drop unknown IDs on refresh. DeletePost is a synchronous batch (ADR-0010 D4) plus one `post_delete` job message for every deleted post (P4/P5: media objects, likes, reposts and their REPOST docs, quote tombstones; ADR-0018 D6); account purge uses `posts.Eraser` (`authorId == uid ORDER BY createdAt DESC LIMIT 500`, self-resuming, then `embeddedAuthorId == uid` copies in other users' docs) and the `engagement` step (likes, reposts, `userLikes`).
- Account deletion: Pub/Sub job batches (≤ 500 ops per batch) over posts, follows, likes, notifications, media objects, graph doc, `postRemovals` entries by `authorId` (posts step phase 2, ADR-0016 amendment 2026-10-18 (b)), `quotas/{uid}` (ADR-0003 amendment 2026-09-30;
  `docs/runbooks/account-deletion.md` Step 2), then the Firebase Auth user. Must be resumable.
- Export: same traversal written to a JSON file in a private GCS object with a 24 h signed URL.
- **Follow-edge invariant (ADR-0009, standing):** for any account that can call graph RPCs (ACTIVE), `follows/{a}_{b}` exists ⇔ `b ∈ graph/{a}.following` ⇔ both `users/{a}` and `users/{b}` exist. Only the account under purge (`DELETING`, rejected by the account-status interceptor) may violate it. This is why Unfollow's blind batch treats a failed precondition as a correct 0-write NONE with no extra read. Every new writer of `follows`, `following` or `users/*` deletes (follow requests, account restore/import, an automated deletion job, T27 extended to `following`) must preserve it and re-check ADR-0009's reopen criteria. ADR-0025 D9 re-checked it for follow requests: accept and the `privacy_public` job create the edge and the `following` entry in one transaction that reads `graph/{a}` and the request fresh, and two invariants join it, I-R and I-X (the `followRequests` row). Deletion is one-way once purge step 1 has run, and `users/{uid}` is deleted only after the purge dry run shows 0/0 edges (`docs/runbooks/account-deletion.md`).

## Migrations
Firestore is schemaless: add fields with defaults in Go structs; backfill with a throttled Cloud Run job (watch the 20k writes/day quota — spread across days or accept a few cents).
Never rename a field in place: add new → dual-write → backfill → switch reads → remove old.
